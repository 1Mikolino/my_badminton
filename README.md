## 闭环图

```
球飞过来 → 感知(看球) → 估计(猜轨迹) → 拦截规划(在哪接)
        → 策略(怎么打回去) → 机械臂/底盘(执行) → 回球
```

**每一步在做什么（一句话）：**

| 环节 | 一句话说明 |
| --- | --- |
| 球飞过来 | 羽毛球从对面打来，是系统的输入信号。 |
| 感知（看球） | 用摄像头/传感器"看见"球，拿到它当前的位置。 |
| 估计（猜轨迹） | 根据现在看到的球，预测它接下来会飞到哪、什么时候到。 |
| 拦截规划（在哪接） | 算出机器人在哪个位置、哪个时间点去接这个球。 |
| 策略（怎么打回去） | 决定这一拍怎么打回去，比如吊球、扣杀还是打高远球。 |
| 机械臂/底盘（执行） | 让机械臂和底盘真的动起来，把拍子挥到规划好的位置。 |
| 回球 | 球被打回去，是系统的输出；对方再打回来即进入下一轮，故为闭环。 |

## 思考题

### 1. 为什么"感知/估计"在理想情况下可以绕开，直接知道球的真实位置？这会给调试带来什么好处？

**核心：在仿真里，物理引擎（MuJoCo）就是"上帝"，它本来就知道球的真实位置和速度，根本不用靠摄像头去猜。**

真实机器人上，球的位置没人直接告诉你，只能靠摄像头拍 → 图像处理 → 滤波估计，一路猜出来，还带噪声、延迟、遮挡、标定误差。

但在仿真里，可以直接向引擎要"球现在在哪、速度多少"——这就是**真值（ground truth）**，也叫"特权信息 / oracle"。相当于开挂：跳过感知和估计，直接把标准答案喂给后面的模块。

**调试上的好处：**

1. **隔离故障源（最大好处）**——链路从 7 环缩短到 5 环，一旦打不中球，立刻知道问题出在规划/策略/控制，不用再怀疑"是不是摄像头标定歪了""是不是滤波器发散了"，排查范围一下小一半。
2. **拿到性能上界**——用真值跑出来的成绩是"理想上限"。之后再接入真实的感知/估计跑一遍对比，就知道感知这一层让性能掉了多少，这个差值就是要优化的目标。
3. **快且可复现**——不用渲染图像、不用跑视觉算法，迭代速度快很多；同样的输入必然得到同样的输出（确定性），方便定位 bug。
4. **可以单独验证估计器**——把"估计出来的轨迹"和"真值轨迹"直接相减算误差，这是检验感知/估计模块最标准的做法。
5. **先打通主链路**——工程上的通用套路：先用标准答案把后半段跑通，再逐步加真实感。先证明"给完美信息我能把球打回去"，再证明"信息不完美时我还能打回去"。

> 顺序建议：**真值 → 打通 规划/策略/控制 → 再接入感知/估计**。反过来先做感知，会同时面对"算法错"和"感知错"两件事，分不清是谁的锅。

### 2. 整个系统为什么按"训练层 → 策略层 → 仿真层"分层？反着依赖会出什么问题？

**核心：分层的本质是"依赖方向必须单向、只能从上往下指"，下层永远不许回头依赖上层。**

**各层职责（各管各的，互不知情）：**

| 层 | 只负责 | 它"不知道"什么 |
| --- | --- | --- |
| **训练层** | 学习循环（采样、算奖励、更新参数） | ——（它是唯一知道"这是个强化学习任务"的地方） |
| **策略层** | 决策：看到球的状态，决定打哪、怎么打 | 不知道自己在仿真还是真机，不知道自己是在被训练还是在比赛 |
| **仿真层** | "世界"：物理、碰撞、机械臂动力学 | 不知道什么是战术，更不知道什么是训练 |

**这么分的好处：**

- **可替换**：仿真层能换成真机，策略层代码一行不用改——这就是 `hal/`（硬件抽象层）存在的意义，仿真和真机实现同一个接口。
- **可测试**：策略层可以配一个极简的假仿真来单测，不用启动整套训练框架。
- **可复用**：仿真层能拿去做别的任务；策略层能直接部署到机器人上。
- **改动不扩散**：换训练算法只动训练层，物理代码完全不受影响。

**反着依赖（下层依赖上层）会炸成什么样：**

- **循环依赖、牵一发动全身**：物理引擎的代码里冒出 `import 训练算法`，改一处崩一片。
- **底层跑不起来**：只想单测一个物理碰撞，结果被迫拖进整个训练框架和它的一堆重依赖。
- **策略无法部署**：策略层一旦依赖训练层，想把它推到真机上，就得把训练代码一起搬过去——真机上多半还跑不起来。
- **测试地狱**：测底层必须先把上层全拉起来，单元测试形同虚设。
- **概念上就是错的**：物理世界不该"知道"你的战术和训练计划。这就像**让地基依赖屋顶**——方向反了，房子必塌。

> 一句话总结：**上层依赖下层是"调用"，下层依赖上层是"反噬"。** 这其实就是软件工程里的**依赖倒置 / 接口隔离**思想——两边都只依赖抽象接口，不依赖对方的具体实现。

### 3. 为什么"参数统一入口"很重要？两个文件都要读物理参数，各自写一遍 `open + yaml.load` 有什么风险？

**核心：统一入口 = "读取逻辑全项目只有一份"。只写一次、只有一处要对，改一处全局生效。**

如果两个文件各自写一遍 `open + yaml.load`，风险有：

1. **行为不一致，同一份 yaml 读出两个结果**——A 用 `yaml.safe_load` 且写了 `encoding="utf-8"`，B 用 `yaml.load` 又没写编码。Windows 下不指定编码会按 GBK 打开，yaml 里的中文注释直接 `UnicodeDecodeError`；而 `yaml.load` 还可能把不可信内容实例化成任意对象，有安全隐患。**同一份配置，一处能读、一处崩。**
2. **报错体验不一致**——你的入口有清晰报错（哪个文件、错在哪），别人那处直接甩一个裸 `FileNotFoundError` 堆栈，连是哪个文件都不说，排查成本翻倍。
3. **改一处、漏一处**——以后要加"环境变量覆盖""路径相对项目根解析""读取缓存""支持 JSON"，你有 N 处要改，必然漏掉某处，而漏掉的那处就是隐藏 bug。
4. **默认值和校验逻辑分裂**——比如"`gravity` 缺省补 9.81""`mass` 必须为正"，两处各写一套，早晚打架。
5. **无法统一替换与测试**——想给配置读取加缓存、加日志、或换成从远端拉配置，没有唯一入口就无从下手；也没法用一个单元测试覆盖全部读取路径。

**统一之后的好处：** 改一行全项目受益，行为一致、报错一致、可测试、可替换。

> 一句话总结：**"全项目只有一个入口"不是为了少写几行代码，而是为了让"读配置"这件事只有一种行为、一个真相来源（single source of truth）。**

### 4. 哪些东西**应该**硬编码（常数、物理恒量），哪些**必须**进配置（球参数、机器参数、阈值）？

**判断标准一句话：定义世界的"事实"硬编码，描述这次实验怎么跑的"选择"进配置。**

**应该硬编码（写死在代码里）：**

- **数学与物理恒量**：π、单位换算系数（度 ↔ 弧度）、`1e-9` 这类数值稳定项。它们是"定义"，不是"可调参数"。
- **语言/框架级不变量**：yaml 一律用 `safe_load`、文件按 `utf-8` 读、数组的维度顺序约定。
- **程序结构常量**：模块名、函数签名、枚举取值、错误码。
- **判定标准**：改了它**代码逻辑本身就错**的东西——那不是参数，是代码的一部分。

**必须进配置（放 yaml）：**

- **球的参数**：质量、半径、阻力系数、空气密度。
- **机器人的参数**：臂长、最大角速度、底盘的速度/加速度档位。
- **感知参数**：帧率、处理延迟、检测概率、噪声标准差。
- **阈值**：判定击中 / 出界 / 收敛的阈值。
- **场地与目标区域**：回球目标区的坐标、优先级。

**判定标准**：改了它**不需要动代码、也不需要翻代码找它在哪**——那它就该进配置。

> 一句话总结：**硬编码的是"什么是真的"（事实），配置里的是"这次我们怎么跑"（选择）。** 换个硬件、换个场地、调个阈值就要改的东西，绝不能写死在代码里。
